## Bugs found and fixed in this session

### B1 — position loop deadlock (app.py)
`background_position_loop()` called `_node_status()` while already holding
`status_lock`, and `threading.Lock` is not reentrant → the loop deadlocked on
its first iteration, holding the lock forever. Every REST request that touched
the lock (`/api/status`) hung. Fix: split out `_nodes_for(state, pos_s)` which
takes no locks; never nest lock acquisition.

### B2 — RTP pacing free-run (player.py) — the big one
```python
if 0 < ahead < 0.1:      # BUG
    time.sleep(ahead)
```
The upper bound silently disabled pacing as soon as the sender ran >100 ms
ahead — which is immediate, since ffmpeg hands the pump 4 frames per read. The
sender then free-ran at ffmpeg's decode rate (~3x real time). Evidence:
position advanced ~3020 ms per 1000 ms of wall clock; board showed
`pkts=358 dropped=45`.
Fix: anchor `_start_wall` on the first sent frame (so ffmpeg spawn/decode delay
is not counted as a deficit) and sleep the whole lead, capped per iteration:
```python
if ahead > 0:
    time.sleep(ahead if ahead < 0.25 else 0.25)
```
Result: 50 pkts/s, dropped=0 (see counters above).

### B3 — position lost on pipeline restart (player.py)
`seek()`/`set_volume()` restart the pipeline and zeroed `_bytes_sent`, so
position restarted from 0 — a seek showed 0:00 and a volume change restarted the
song from the beginning. Fix: added `_base_samples` (samples played before the
current pipeline); `sample_position = _base_samples + _bytes_sent/2`; `seek()`
rebases on the requested absolute position; `set_volume()` now does
`self.seek(self.sample_position)` (restart at the current position, smaller diff
than the old stop+play).

### B4 — natural EOF left the player "playing" (player.py)
`_pump()` called `_status_cb(state="stopped")` on ffmpeg EOF but never cleared
`_running`, so `sample_position` kept returning the last byte count and the UI
stayed "playing" forever on a finished file. Fix: clear `_running`, kill the
pipeline, then report `stopped` — identical to a manual stop.

## Environment gotchas hit (worth remembering)
- Orphaned `idf_monitor` python processes keep COM5 open → `Stop-Job` does not
  kill the grandchild; kill by PID via
  `Get-CimInstance Win32_Process -Filter "Name='python.exe'"`. Symptom: monitor
  attaches and prints nothing while another process holds the port.
- Opening COM5 with pyserial + `setDTR(False)/setRTS(False)` **resets the
  board** (log starts at ESP-ROM boot). Fine for tests, but don't confuse it
  with a crash.
- `taskkill /F /IM python.exe /T` kills the Flask server too — restart it after
  cleanup if the next step needs it.
- **Never `Start-Job` a long build and then keep issuing shell commands**: the
  tool closes the previous terminal on each new command, which kills the job's
  process tree — the build log restarted twice (979 → 1088 targets) before this
  was understood. For long builds either run them as the only command, or launch
  detached (`Start-Process pwsh -File tmp\build_fw.ps1 -WindowStyle Hidden`).
